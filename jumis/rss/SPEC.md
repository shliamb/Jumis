# SPEC: rss

## Суть работы

Мировые новости из RSS-фидов: забор, сведение сюжетов в одну сводку со сносками на источники, накопление сводок в БД.

Модуль делит работу между кодом и моделью:

- **Код** (`fetcher.py`) — тянет все фиды параллельно, разбирает RSS 2.0 / RSS 1.0 (RDF) / Atom, чистит HTML, режет описания, склеивает дубли, следит за здоровьем источников. Ноль токенов.
- **Модель** (`analyst.py`) — один вызов на сводку: группирует одно событие из разных фидов, ставит сноски «кто это сказал», показывает расхождения версий, отделяет свои оценки. Единственное место, где тратятся токены.
- **Фасад** (`__init__.py`, `RssNews`) — порядок работы: кэш → забор → окно → анализ → запись → статусы фидов.

Сводка хранится двумя частями: `body` (полный текст со сносками) и `gist` (3–5 строк сути) — чтобы через год поднять картину одним дешёвым запросом, не читая километры текста.

## Входные данные

**Фиды** — строки таблицы `rss_feeds`: `url`, `title`, `note` (свободная пометка «РФ, государственное»), `active`.

- Стартовый набор из 10 фидов (`fetcher.DEFAULT_FEEDS`) заводится один раз, если таблица пуста.
- Интернет: `httpx` (таймаут 20 с, не более 8 фидов одновременно, `MAX_FEEDS=20`), разбор — `lxml`.
- Форматы: RSS 2.0 (`item/pubDate`), RSS 1.0/RDF (`item/dc:date`, DW), Atom (`entry/published`).
- Админка: список фидов построчно — `URL` или `URL | заметка`; можно дать адрес сайта, фид найдётся через `<link rel="alternate">`.
- Инструмент `rss_feeds_edit`: `add` (один URL) / `remove` (id, точный URL или часть названия) / `note`.

**Параметры сводки:** `hours` (по умолчанию 12, максимум 72), `per_feed` (по умолчанию 10, максимум 25), `fresh` (игнорировать кэш).

**Что модель получает на вход** (`analyst.render_input`): записи, сгруппированные по фидам, с названием фида, его заметкой и временем каждой записи. Потолок входа — 45000 символов: сначала режутся описания до 120 символов, затем отбрасываются хвостовые (самые старые) записи.

## Выходные данные

**Строка `rss_digests`**: `id`, `created_at`, `period_from`, `period_to` (TIMESTAMPTZ, UTC), `gist` (3–5 строк), `body` (полный текст: сюжеты со сносками + блок «Выводы (оценка)»), `items_count` (записей в окне), `feeds_used` (фидов, чьи записи попали в окно), `feeds_failed` (кто не ответил), `model`.

**Формат `body`** — markdown:

```
### Название сюжета
- Что произошло (Источник).
- По версии X: что утверждает другая сторона (Источник).

---

**Выводы (оценка)**
- Что из этого следует, где картина расходится.
```

**Ответ модели** разбирается по трём маркерам: `ВЫЖИМКА:` → `gist`, `СВОДКА:` → `body`, `ВЫВОДЫ:` → приклеиваются к `body` отделённым блоком. Маркеров нет — весь текст считается сводкой, выжимка берётся из первых содержательных строк.

**Методы фасада** (`RssNews`): `collect(hours, fresh, per_feed)` → `{ok, cached, digest, failed, error?}`; `feeds(active_only)` → список с полем `status`; `check_all()` → отчёт по каждому фиду; `add_one(url, note)`, `remove_one(ident)`, `replace_from_text(text)`; `archive(days, query, limit, with_body)`, `read(digest_id)`, `stats()`.

**Статусы фида** (`status_of`): `ok` — отвечает и свежий; `new` — ни разу не проверялся; `warn` — были падения; `stale` — нет новых записей 14 дней; `dead` — 3 падения подряд.

**Инструменты агенту:** `rss_digest`, `rss_archive` (короткие выжимки за период или полная по `digest_id`), `rss_feeds`, `rss_feeds_edit`.

## Логика (Вариации)

**Порядок `collect()`** (под `asyncio.Lock`, параллельный второй вызов получает `error="busy"`):

1. `fresh=False` и есть сводка моложе `CACHE_MINUTES=120` → отдаём её с `cached=True`, модель не зовём.
2. Берём активные фиды; пусто → `error` «нет активных источников».
3. `fetch_all` параллельно; по каждому фиду `mark_ok` / `mark_fail`.
4. `_window` — оставляем записи в окне `[now-hours, now]`. Записи без даты берём только если датированных нет вообще (максимум 15).
5. Записей меньше `MIN_ENTRIES_TO_ANALYZE=3` → отказ с перечислением не ответивших.
6. `analyst.analyze` — один вызов `simple_call(system, dialog=[], timeout=180)`: свой промпт, **пустой диалог**, история владельца в запрос не попадает.
7. `save_digest` → id; `feeds_used` считается по фидам, чьи записи реально попали в окно.

**Замена списка** (`replace_from_text`): каждый адрес проверяется сетью до сохранения; принятые сохраняются, отклонённые перечисляются с причиной. Не прошёл ни один → старый список не трогаем. Пустой разбор → отказ.

**Дискавери**: если по URL пришла не лента, ищем `<link rel="alternate" type="application/rss+xml">`; явно сообщаем в отчёте, какой адрес подставлен. Если объявления нет — пробуем `/rss`, `/feed`, `/rss.xml`, `/feed/`.

**Дедупликация** в одном запуске — по ссылке и по нормализованному заголовку. Склейка одного сюжета из разных фидов — работа модели, не кода.

## Обработка ошибок

- **Фид не ответил** (таймаут, 403, 404, 5xx): `mark_fail`, `fail_count += 1`, `last_error` — текст причины. Сводка всё равно собирается из остальных; не ответившие перечисляются в `feeds_failed` и попадают в сноску в чате.
- **Фид ответил, но записей нет** (частый случай у закрытых изданий) — считается падением с причиной «фид ответил, но записей нет».
- **Модель вернула текст ошибки** вместо сводки (`LLMWorker` при сбое подставляет текст исключения в `content`): `analyst.looks_like_error` ловит маркеры («Ошибка сети», `litellm.`, `BadRequestError`, `model parameter is required` и др.), сводка **не сохраняется**, `collect` возвращает `error="модель не дала сводку"`.
- **Таймаут модели**: сводка — длинная генерация, общего лимита 30 с не хватает; для этого вызова передаётся `LLM_TIMEOUT=180`. Общий `LLM_TIMEOUT` не меняется.
- **Одновременный сбор** (кнопка + агент + крон): второй вызов получает `busy`, ничего не пишется.
- **Плохой URL в админке**: `http(s)` обязателен (домен дополняется схемой); ответ проверяется на XML; ошибка возвращается в отчёт, список не меняется.
- **Все адреса в замене битые**: список не заменяется, старый остаётся рабочим.
- **Дата в будущем** (RDF-фиды без часового пояса): прижимается к «сейчас», иначе такая запись вечно висела бы первой.
