# SPEC: memory

## Суть работы

Память как три слоя вместо одной кучи фактов.

1. **Разделы в промпте** — факты в `memories`, у категории которых `facts_categories.in_prompt = TRUE` (правила, стили, паспорт владельца). Рендерятся в system-промпт на каждый запрос, поэтому правка видна уже в следующем ответе.
2. **Карта памяти** — генерируемое оглавление архива: полки (категории без `in_prompt`), число живых фактов и описание. Не содержание — подсказка, где искать.
3. **Архив** — обычный векторный поиск `search_facts`, плюс «подхват»: несколько фактов, возможно относящихся к входящему сообщению, подмешиваются в промпт без вызова инструментов.

Дубли не удаляются, а помечаются: `memories.memory_status = 'superseded'` (есть замена) или `'archived'` (устарело без замены) и `superseded_by = <id канона>`. История остаётся в базе, поиск и рендер видят только `live`.

Устройство: `render.py` — чистые функции форматирования; `__init__.py` — фасад `Memory` (блоки промпта, подхват, поиск похожих, сводка); `cleaning.py` — `MemoryCleaner` (ночная склейка дублей и отложение гнилых фактов).

## Входные данные

- `db_memory` (`DBMemories`): `get_prompt_sections`, `get_section_facts`, `get_map_rows`, `search_vectors`, `find_similar_pairs`, `get_facts_by_ids`, `fetch_relative_dated`, `mark_superseded`, `add_fact`, `live_stats`, кэш `fact_categories`.
- `embedder` (`vector.embedder`): `get_embedding(text, is_query=...)`.
- `llm` (необязательно): `simple_call(system, dialog, question, timeout)` — только для уборки; без него `Memory.cleaner = None`.
- Текст запроса владельца — для `recall`.
- Пороги (константы): `DUP_SIMILARITY = 0.93`, `RECALL_TOP = 3`, `RECALL_MIN_SIMILARITY = 0.85`, `MIN_FACT_CHARS = 20`; в уборке `MERGE_MIN_SIMILARITY = 0.93`, `MAX_GROUP_SIZE = 8`, `MAX_GROUPS_PER_RUN = 20`, `STALE_DAYS = 21`.

## Выходные данные

- `Memory.prompt_blocks()` → str: `## TITLE` + строки `- [#id] текст` для каждого непустого раздела (в порядке `prompt_order`) и блок `## MEMORY MAP`.
- `Memory.recall(text)` → str: блок `## POSSIBLY RELEVANT TO THIS REQUEST` с 1–3 фактами архива или пустая строка.
- `Memory.similar(content, embedding, min_similarity, limit)` → `list[dict]` живых фактов с `similarity`.
- `Memory.stats()` → `{live, archived, total, categories}`; `Memory.cleaner.scan()` → `{pairs, groups, in_groups, stale, live, archived}`; `MemoryCleaner.run_night(max_groups)` → `{groups, merged, skipped, superseded, stale, errors}`.
- У каждого отрендеренного факта виден его `#id` — по нему агент правит через `update_fact`, не разыскивая заново.

## Логика (Вариации)

1. `prompt_blocks`: разделы берутся из `facts_categories WHERE in_prompt ORDER BY prompt_order`; факты раздела — `WHERE category = $1 AND memory_status = 'live' ORDER BY id ASC`. Карта строится по категориям с `in_prompt = FALSE` и считает только живые факты; полки с нулём пропускаются.
2. Бюджеты рендера: `profile` 5200 символов, `rule` 2400, каждый `style_*` 1000, общий потолок 12000. Факт длиннее 400 символов режется по слову; не влезшие факты заменяются строкой «…N more facts on this shelf…». Поэтому паспорт рендерится целиком, а промпт не растёт бесконечно.
3. Подхват: текст короче 3 символов и системные триггеры (`[SYSTEM TRIGGER…`) не подхватываются. Вектор запроса считается с `is_query=True` (у e5 префиксы `query:`/`passage:` разные), поиск идёт с `include_sections=False` — разделы в промпте уже есть. Порог 0.85 откалиброван на живой базе: реальные попадания 0.85–0.88, шум 0.78–0.84.
4. Защита от дублей стоит на записи (`functions.write_fact`): вектор считается один раз, затем `Memory.similar` ищет живые факты с близостью ≥ 0.93; при попадании факт **не пишется**, а возвращается `NOT SAVED` с id и текстом похожего — агент обязан вызвать `update_fact`.
5. `search_vectors` никогда не возвращает не-`live` факты. `get_all_facts` (бэкап) возвращает всё — данные не теряются.
6. Уборка (`MemoryCleaner.run_night`): пары живых фактов с близостью ≥ 0.93 → union-find в группы (группы больше 8 режутся — это цепочки, а не дубли) → одна модель на группу пишет канонический текст 20–1500 символов и список покрытых id. Канон вставляется новой строкой с вектором, покрытые факты получают `superseded`.
7. Если в группе есть факт из раздела промпта, канон принудительно остаётся в этом разделе (иначе строка выпадет из промпта в архив). Если модель вернула `action: "skip"`, назвала меньше двух покрытых id или категорию вне списка — группа не склеивается.
8. Устаревшее: живые факты старше 21 дня с относительными датами («сегодня», «вчера», «завтра», «сейчас»…) получают `archived`. Восстановление — обратной установкой `memory_status = 'live'`; ничего не удаляется.
9. Ночью уборка идёт последним шагом `Cleaner.nightly` (после уборки истории и самаризации), не больше 20 групп за прогон.

## Обработка ошибок

- Любая ошибка сборки блоков или подхвата → пустая строка + `logger.error`: память не должна ломать ответ агента.
- Файл промпта `llm/prompts/jumis_agent.md` отсутствует или пуст → `load_prompt` возвращает короткую английскую заглушку, бот поднимается.
- Модель в уборке вернула текст ошибки (`Ошибка сети: …`) → `_looks_like_error` отбрасывает, группа пропускается; исключение → `errors += 1`, остальные группы продолжаются.
- Ответ модели не JSON (в т.ч. в ```-блоке) → `_parse_json` → `None`, склейки нет.
- Эмбеддинг канона не получен → факт всё равно пишется (без вектора), ночью его догонит `write_fact`-фолбэк; при ошибке эмбеддинга в `write_fact` — фоновая дозапись.
- Вставка канона не удалась → покрытые факты не трогаются (не теряем данные).
