# SPEC: pgbackup

## Суть работы

Логический бэкап базы данных в файл. `pg_dump` пишет сжатый custom-формат в `jumis/backups/` (в контейнере — `/jumis/backups`, тот же каталог на хосте через том), после успешного дампа старые копии сворачиваются до трёх.

Утилита запускается по-разному:
- на хосте — `docker exec jumis_postgres pg_dump ...`: хостовый клиент 14 отказывается дампить сервер 17, а внутри контейнера версия совпадает и пароль не нужен (unix-сокет);
- в контейнере бота (`IN_DOCKER=1`) — локальный `pg_dump` 17 из образа по сети на `DB_HOST:DB_PORT` с `PGPASSWORD`: docker CLI и docker.sock боту не нужны.

Модуль только читает базу и пишет файлы: рабочие таблицы не меняются. Восстановление — ручная операция владельца (`docker exec -i ... pg_restore`, утилита есть в образе postgres).

## Входные данные

- `db_tasks` (`DBTasks`), `scheduler` (`register_system_task`).
- Параметры подключения из `config`: `DB_NAME`, `USER_DB`, `PASSWORD_DB`, `DOCKER`, `HOST`, `PORT`, `PATH_BACKUPS`.
- В режиме хоста — контейнер `jumis_postgres` (имя стабильно, задаётся в `docker-compose.yml`). В режиме контейнера он не нужен: `pg_dump` стоит в образе бота.

## Выходные данные

- Файлы `jumis/backups/jumis_YYYY-MM-DD_HHMMSS.dump` (custom-формат `-Fc`, сжатый; сейчас ≈33 МБ).
- Не более `KEEP_COPIES = 3` файлов; остальные удаляются после успешного нового дампа.
- Отчёт `create()`: `{ok, name, path, size, size_human, duration, deleted, keep}` либо `{ok: False, error}`.
- Одна строка `scheduled_tasks`: `tg_id = NULL`, `task_type = 'system_cron'`, `title = 'Ночной бэкап базы данных'`, `cron_expression = '30 4 * * *'`.
- Инструменты агенту: `backup_now`, `backup_list`; команды владельцу: `/backup`, `/backup_now`, `/backups`.
- Логи: `[Backup]`, `[SysCron]`.

## Логика (Вариации)

1. `DBRunner.create()`: дамп пишется в `<имя>.dump.part`; после проверки файл атомарно переименовывается — в папке не бывает полуфайлов с боевым именем.
2. Проверка дампа не на веру: размер ≥ 1 КБ и сигнатура `PGDMP` (первые 5 байт custom-формата).
3. Команда зависит от режима: на хосте `docker exec jumis_postgres pg_dump -U <USER_DB> -d <DB_NAME> -Fc` (unix-сокет, пароль не нужен); в контейнере `pg_dump -h <DB_HOST> -p <DB_PORT> -U <USER_DB> -d <DB_NAME> -Fc` с паролем в `PGPASSWORD` (ни в лог, ни в argv он не попадает).
4. Таймаут дампа 30 минут; по истечении процесс убивается, `.part` удаляется, возвращается ошибка.
5. Ротация: файлы сортируются по имени (в имени ISO-время), остаются `keep` последних; хвостовые `.part` от упавших прогонов вычищаются. Удаление — **только после** успешного нового дампа.
6. `Backups.nightly(task)` — по крону 04:30 (на час позже уборки, чтобы дамп снимался уже с почищенной базы): один дамп + ротация, защита от повторного входа (`_nightly_running`), наружу не бросает.
7. `ensure_system_task()` создаёт/оживляет строку крона; `cancelled` — уважает; `del_task` для неё запрещён, `update_task` разрешает только `status` (общая механика в `utils/system_cron.py`).
8. Запуск сразу двух дампов (кнопка + крон) блокируется `asyncio.Lock`: второй получает `error = "already_running"`.
9. В дамп попадают и `chat_digests`, и строка системного крона — после восстановления крон встаёт сам при первом старте.
10. Отсутствие нужной утилиты (в контейнере `pg_dump`, на хосте `docker`) — явная ошибка («не найден pg_dump/docker»), а не тихий пропуск.

## Восстановление (вручную)

Автоматического восстановления нет: это разовая операция владельца, база при ней должна быть свободна.

1. Остановить бота (иначе пул держит соединения и `--clean` не сможет удалить таблицы).
2. Снять страховочную копию текущего состояния: `/backup_now` (или `pgbackup.runner.DBRunner.create()`), чтобы шаг 4 можно было откатить.
3. Посмотреть состав файла: `docker exec -i jumis_postgres pg_restore --list < файл.dump`.
4. Восстановить **в новую базу** (безопасный путь, боевая не трогается):

```bash
docker exec jumis_postgres createdb -U <user> jumis_restore
docker exec -i jumis_postgres pg_restore -U <user> -d jumis_restore --no-owner --no-acl < jumis_YYYY-MM-DD_HHMMSS.dump
```

5. Проверить числа (`SELECT count(*) FROM messages/users/chat_digests`), и только потом переключить `POSTGRES_DB` в `.env` на `jumis_restore` (или переименовать базы) и запустить бота.

Восстановление **поверх текущей боевой базы** (необратимо удаляет объекты в целевой БД):

```bash
docker exec -i jumis_postgres pg_restore -U <user> -d <db> --clean --if-exists < jumis_YYYY-MM-DD_HHMMSS.dump
```

Одна таблица (например, только `users`): `pg_restore -d <db> --data-only --table=users < файл.dump`.

После восстановления системные кроны (уборка 03:30, бэкап 04:30) уже лежат в дампе; при первом старте `ensure_system_task()` проверит их и оживит, если время уехало в прошлое.

## Обработка ошибок

- `pg_dump` вернул не 0 (база не запущена, нет прав, неверный пароль) → `{ok: False, error}` с текстом stderr (до 500 символов); файла не остаётся.
- Нет нужной утилиты (`pg_dump` в контейнере, `docker` на хосте) → `BackupError` с именем утилиты.
- Файл меньше 1 КБ или без сигнатуры `PGDMP` → `BackupError`, `.part` удаляется.
- Папка недоступна (нет прав) → `{ok: False, error}`.
- Дамп не уложился в 30 минут → процесс убит, ошибка.
- Ошибка ротации → логируется, но дамп считается успешным (свежая копия важнее).
- Ночной прогон падает внутри → ловится и логируется, планировщик получает управление обратно.
